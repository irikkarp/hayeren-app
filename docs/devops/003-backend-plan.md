# Фича 003: план бэкенда (аккаунты через Telegram и синхронизация)

Статус: предложение на согласование. Ничего не установлено, не зарегистрировано и не опубликовано; к серверу доступа нет. Исследование сделано без веб-поиска, по знаниям на момент написания: всё, что стоит перепроверить перед реализацией, помечено **«проверить»**.

Входы: `docs/PRODUCT.md` (решения 2026-10-23), `docs/dev/architecture.md` (модель данных под синхронизацию), `docs/devops/README.md`, `docs/devops/deploy-plan.md`. План обновлён 2026-10-24 под `docs/requirements/003-accounts-sync.md` ред. 2 (раздел L) и решения контролёра.

## Сводка рекомендаций

1. HTTPS без домена: `<ip-через-дефисы>.sslip.io` + Caddy (автосертификат Let's Encrypt, запасной ZeroSSL). Адрес API в клиенте задаётся через `VITE_API_URL`. Домен купить до публичного релиза и до Capacitor-сборки.
2. Вход: через бота с одноразовым кодом (deep link `t.me/<bot>?start=<nonce>`), бот работает через long polling. Login Widget не используем как основной (проблемы в iOS PWA), Mini App не подходит.
3. Сессии: непрозрачный токен в заголовке `Authorization: Bearer`, не cookies. CORS только для `https://irikkarp.github.io`.
4. Стек: Node 22 + TypeScript + Fastify + SQLite (WAL), SQL-миграции, общий пакет доменных типов с клиентом. Docker Compose: `caddy` + `api`.
5. Синхронизация: `push` пачкой изменений и `pull` по серверному курсору (`seq`), сервер применяет ту же общую функцию слияния, что и клиент (пакет `shared/`), по хранилищу; правила между записями (наборы и слова) выполняются в той же транзакции.
6. Безопасность и эксплуатация: токен бота только в файле на сервере (chmod 600), ufw + SSH по ключу, rate limit, ночной бэкап SQLite с копией вне сервера.
7. CI/CD: код в `server/` того же репозитория, образ собирается в GitHub Actions и кладётся в ghcr.io, деплой по SSH под ограниченным пользователем с ручным подтверждением; откат на предыдущий тег образа.

## 1. HTTPS без собственного домена

Зачем HTTPS обязательно: фронтенд на `https://irikkarp.github.io`, браузер запретит запросы к `http://` API (mixed content). Сертификат нужен от доверенного центра, самоподписанный не подойдёт.

| Вариант | Надёжность | Простота | Бесплатно | Let's Encrypt | Telegram | Комментарий |
|---|---|---|---|---|---|---|
| sslip.io / nip.io (`1-2-3-4.sslip.io` резолвится в 1.2.3.4) | средняя: зависит от чужого DNS-сервиса на волонтёрской основе; адрес привязан к IP | максимальная: без аккаунтов и токенов | да | HTTP-01 и TLS-ALPN-01 работают (Caddy сам). Риск лимитов LE на общий домен: если sslip.io не в Public Suffix List, лимит 50 сертификатов в неделю на зарегистрированный домен общий для всех пользователей сервиса. **Проверить** статус в PSL и текущие лимиты LE | вебхук не нужен при long polling; вебхук с этим сертификатом тоже был бы принят (**проверить**) | Хороший старт. Если сервис недоступен, не продлится сертификат и клиенты не найдут API |
| DuckDNS (`имя.duckdns.org`) | средняя: бесплатный сервис, были перебои; имя не привязано к IP | простая: вход через GitHub/Google, токен для обновления IP (на статичном IP не нужен) | да | HTTP-01 работает; DNS-01 через плагин. Лимиты LE общие на `duckdns.org` (**проверить** PSL) | то же | Стабильное имя независимо от IP, удобно при переезде сервера. Требует аккаунт владельца |
| Cloudflare Tunnel | высокая сама по себе | быстрые туннели (`trycloudflare.com`) выдают случайный адрес, меняющийся при перезапуске, для продакшена не годятся; именованный туннель требует домен в Cloudflare | да (при наличии домена) | не нужен, сертификат Cloudflare | да | Без домена не подходит |
| Tailscale Funnel (`машина.tailnet.ts.net`) | средняя | простая, но ещё один агент и аккаунт | да (личный план) | сертификат выдаёт Tailscale | да | Есть лимиты трафика, зависимость от стороннего сервиса. Запасной вариант (**проверить** условия) |
| Купить домен | высокая | регистратор + A-запись | ~2–12 USD/год | любой способ, DNS-01 возможен | да | Единственный вариант без зависимости от чужого DNS |

**Рекомендация.** Старт на sslip.io: ничего не регистрируем, Caddy получает сертификат сам и при проблемах с Let's Encrypt автоматически пробует ZeroSSL. Адрес API не вшивается в код, а берётся из `VITE_API_URL` на сборке (GitHub Variables, не Secrets: адрес публичный). Если у sslip.io начнутся проблемы, переключаемся на DuckDNS за час, сменив переменную и пересобрав фронтенд.

**Когда покупать домен:**
- до публичного релиза не только для знакомых;
- до сборки Capacitor-приложений (адрес API попадёт в опубликованный в сторах бинарник, сменить его можно только релизом);
- если понадобятся Login Widget или Mini App (им нужен нормальный домен);
- если сервер придётся перенести на другой IP (с sslip.io адрес поменяется).
Домен недорогой, для бэкенда достаточно поддомена `api.<домен>`. Фронтенд может остаться на github.io.

Важно: IP-адрес на Vultr должен быть статичным (по умолчанию да, пока инстанс не пересоздан). Если у сервера есть только IPv6 или IP меняется, схема ломается (**уточнить у владельца**).

## 2. Вход через Telegram

### Сравнение

| Критерий | Login Widget | Вход через бота (одноразовый код / deep link) | Mini App |
|---|---|---|---|
| Требует `/setdomain` | да | нет | нет (но приложение открывается внутри Telegram) |
| Работает с фронтендом на github.io | возможно, но см. ниже | да, фронтенд не участвует в протоколе Telegram | не подходит: наш фронтенд обычная PWA в браузере |
| Установленная iOS PWA | плохо: виджет открывает всплывающее окно/редирект на `oauth.telegram.org`, в standalone-режиме iOS это нестабильно; редирект выбрасывает из PWA | хорошо: Telegram открывается другим приложением, PWA остаётся, опрашивает сервер | не применимо |
| Нужен ли вебхук | нет | не нужен при long polling | зависит |
| Cookies и третьи стороны | виджет в iframe, на Safari мешает ITP | не нужны | не применимо |
| Подтверждение личности | подпись `hash` на сервере | Telegram сам передаёт `from.id` боту, подделать нельзя | подпись `initData` |
| Пользователь без установленного Telegram на этом устройстве | вводит телефон на oauth.telegram.org, подтверждает в Telegram на другом устройстве | нужен Telegram на этом же устройстве (или перейти по ссылке/QR с другого) | нужен |

**Про `/setdomain`.** В BotFather указывается домен (без пути), с которого загружается виджет. Для нашего фронтенда это было бы `irikkarp.github.io` (путь `/hayeren-app/` не указывается, проверка идёт по origin). Ограничения, которые нужно **проверить**: принимает ли BotFather домен второго уровня на общем хостинге `github.io` (он в Public Suffix List), и то, что на этом домене могут жить чужие страницы, но без доступа к токену бота это только репутационный риск. Пока это не проверено на реальном боте, строить на виджете основной путь нельзя. Также **проверить**, есть ли у Telegram новый OIDC-вход («Log in with Telegram» с `id_token`/PKCE, с разрешёнными origin в настройках бота): если есть и работает в PWA, это может стать вторым способом входа позже.

### Рекомендация: вход через бота

Сценарий:
1. Клиент: `POST /auth/start` -> сервер создаёт запись `login_requests(nonce, created_at, expires_at 5 мин, status=pending)`, отвечает `{ nonce, deepLink: "https://t.me/<bot>?start=<nonce>", expiresAt }`. Nonce: 128 бит случайности, base64url (допустимые символы payload: A-Z a-z 0-9 _ -, до 64 знаков; **проверить**).
2. Пользователь нажимает «Войти через Telegram», открывается чат с ботом, жмёт «Start».
3. Бот (long polling `getUpdates`) получает `/start <nonce>` с `message.from.id`, находит pending-запрос, помечает его `confirmed` и привязывает `telegram_id` (создаёт пользователя, если его нет). Бот отвечает «Вы вошли, вернитесь в приложение».
4. Клиент опрашивает `POST /auth/poll { nonce }` каждые 2 секунды (до 5 минут). Когда статус `confirmed`, сервер один раз отдаёт сессионный токен и помечает запрос использованным. Повторный запрос с тем же nonce возвращает ошибку.
5. Запасной путь: клиент показывает запасную ссылку с кнопкой «Скопировать ссылку» (требование 7). Запасной 6-значный код не делаем (решение контролёра).

Почему long polling, а не вебхук: серверу не нужно принимать входящие запросы от Telegram, меньше требований к сертификату и маршрутизации. Ограничение: только один процесс может опрашивать `getUpdates` для одного токена, поэтому один экземпляр API. Нагрузка ничтожна.

Безопасность потока: nonce одноразовый, короткоживущий, привязан к клиентскому секрету (клиент генерирует `verifier`, шлёт хеш в `start`, показывает оригинал в `poll`, как PKCE), чтобы перехват deep link не позволил чужому забрать сессию. `telegram_id` берётся только из апдейта Telegram.

**Проверка подписи (если когда-либо подключим Login Widget или Mini App).** Только на сервере: `secret = SHA256(bot_token)`, `hash = HMAC_SHA256(secret, data_check_string)`, где строка собирается из полей по алфавиту `key=value` через `\n`, без `hash`; сравнивать константным по времени сравнением; проверять свежесть `auth_date` (например, не старше 5 минут). Для Mini App `secret = HMAC_SHA256("WebAppData", bot_token)` (**проверить** по актуальной документации). В браузер токен бота не попадает ни при каком варианте.

### Сессии, CORS, iOS PWA

- **Токены в заголовке, не cookies.** Фронтенд (`irikkarp.github.io`) и API (`*.sslip.io`) на разных сайтах. Cookie были бы third-party: Safari ITP и режим PWA их режут, нужен `SameSite=None; Secure` и всё равно ненадёжно. Bearer-токен работает везде и проще для Capacitor.
- Токен: 256 бит случайности, на сервере хранится только его SHA-256, срок 90 дней со скользящим продлением, отзыв по запросу «Выйти» и при удалении аккаунта. Клиент хранит его в IndexedDB рядом с остальными данными (доступен service worker'у; XSS-риск принимаем, приложение не рендерит чужой HTML, CSP это подкрепит).
- **CORS:** `Access-Control-Allow-Origin: https://irikkarp.github.io` (точное совпадение, без `*`; origin не содержит пути), методы `GET, POST, DELETE, OPTIONS`, заголовки `Authorization, Content-Type`, `Access-Control-Max-Age: 86400`, без `credentials`. Для локальной разработки отдельный список в переменной окружения (`CORS_ORIGINS`, на проде только github.io).
- **iOS PWA:** синхронизация только при открытом приложении (Background Sync на iOS недоступен): синк при запуске, при возвращении в приложение (`visibilitychange`), после изменений с задержкой и по кнопке. Хранилище IndexedDB в PWA на iOS может очищаться при долгом неиспользовании в Safari-вкладке, поэтому аккаунт и есть защита от потери данных.

## 3. Стек бэкенда

| Что | Решение | Причина |
|---|---|---|
| Язык | Node.js 22 LTS + TypeScript | те же типы и валидаторы, что и в клиенте; тот же тулчейн, что в CI |
| Фреймворк | Fastify (альтернатива Hono) | зрелый, встроенные схемы валидации, плагины `@fastify/cors`, `@fastify/rate-limit`, `@fastify/helmet` |
| База | SQLite (WAL) через `better-sqlite3` | один файл, нет отдельного сервиса, хватает на тысячи пользователей; backup одной командой. PostgreSQL нужен, только если понадобится несколько экземпляров API |
| Миграции | простые нумерованные `.sql` файлы + таблица `schema_migrations`, запуск при старте контейнера | минимум зависимостей; альтернатива Drizzle Kit |
| Общие типы | пакет `shared/` (типы записей, валидаторы zod) либо npm workspaces `app/`, `server/`, `shared/` | требует аккуратного рефакторинга клиента, вынести в отдельную задачу |
| Reverse proxy | Caddy 2 | автоматический сертификат и продление, HTTP/2/3, 5 строк конфига; оценка: лучший выбор для маленького проекта |
| Запуск | Docker Compose (`caddy`, `api`, тома `caddy_data`, `./data`) | воспроизводимо, откат сменой тега. Альтернатива systemd + Node на хосте проще по памяти, но хуже по воспроизводимости |

### Модель хранения

Универсальная таблица записей, чтобы не менять схему при изменении клиентской модели:

```
users(id, telegram_id UNIQUE, first_name NULL, created_at)   -- фото профиля не сохраняем
sessions(token_hash PK, user_id, created_at, last_used_at, expires_at)   -- device_label не заводим и не заполняем (не храним браузер и ОС)
login_requests(nonce_hash PK, verifier_hash, status, user_id NULL, expires_at)
records(user_id, store, key, data JSON, updated_at, deleted_at NULL, seq INTEGER, PRIMARY KEY(user_id, store, key))
user_seq(user_id PK, last_seq)   -- счётчик курсора на пользователя
```

Синхронизируются хранилища `settings`, `progress`, `days`, `celebrations`, `userSets`, `userWords`. Не синхронизируется `meta` (в том числе `lastBackupAt`). Размер данных на пользователя: порядка сотен КБ.

### API синхронизации

- `GET /sync/pull?cursor=<seq>&limit=500` -> `{ changes: [{ store, key, data, updatedAt, deletedAt, seq }], nextCursor, hasMore }`. Курсор это серверный монотонный `seq`, а не `updatedAt`: так не теряются записи с одинаковыми или «опоздавшими» метками времени с других устройств.
- `POST /sync/push { changes: [{ store, key, data, updatedAt, deletedAt }] }` (до ~500 записей, идемпотентно) -> `{ applied, rejected: [...], serverTime }`. Для каждой записи сервер вызывает ту же общую функцию слияния из `shared/`, что и клиент (правила 32-34 требований: `progress` - победитель целиком плюс максимум счётчиков, `days` - множество дней и максимум полей, `celebrations` - по своему правилу). Чистое «последняя запись побеждает» не используется: устаревшая копия с поздней отметкой не должна откатывать прогресс. Если результат слияния отличается и от сохранённой, и от пришедшей версии, записи присваивается новый `seq`, иначе другие устройства её не получат.
- Ничья по `updatedAt`: надгробие побеждает живую запись; во всех остальных случаях побеждает версия, уже принятая сервером.
- Правила между записями (целостность наборов и слов, объединение одноимённых наборов и дублей, правила 30-31): одна общая функция из `shared/`. На клиенте она выполняется после pull, на сервере - в той же транзакции SQLite, что и запись изменений. Результат должен быть одинаковым везде (требование 39).
- `updatedAt` из будущего (дрейф часов клиента) обрезается до `serverTime + 5 мин`.
- Надгробия хранятся на сервере бессрочно (решение контролёра): чистку через 90 дней не делаем, иначе устройство, давно не выходившее на связь, воскресило бы удалённое. Объём ограничен лимитами на записи.
- Первый вход: клиент делает `pull` до конца, затем `push` всего локального. Если у аккаунта уже есть данные (вход с другого устройства), работает то же слияние по записям. Вопрос про `days` и `progress` решён аналитиком: правила 32 и 33. Если у аккаунта превышаются лимиты после слияния, слияние не применяется ни в одну сторону (требование 37).
- Прочее: `GET /me`, `POST /auth/logout`, `DELETE /account` (удаление всех данных пользователя, нужно для приватности), `GET /health`.
- Версионирование: префикс `/v1`, поле `schemaVersion` в запросе; сервер отвечает `426`, если клиент слишком старый.
- Лимиты: тело запроса до 1 МБ, лимиты по требованию 70: до 3000 живых своих слов, 100 наборов, `progress` до 10 000 записей (запас под 004), `days` до 1500, не более 60 запросов в минуту на аккаунт и 10 одновременно действующих токенов (11-й вытесняет самый старый по последнему использованию). Общий потолок записей на пользователя, включая надгробия, отметки и `settings`: 25 000 (сумма 3000 + 100 + 10 000 + 1500 + отметки уже около 15 000, надгробия бессрочные, поэтому запас). При превышении сервер не принимает лишнюю часть, клиент показывает сообщение о лимите.

### Эксплуатация

- **Бэкапы:** ежедневно `sqlite3 data/app.db ".backup ..."` + gzip, хранить 14 копий на сервере и одну копию вне сервера: либо Vultr Backups (платно, ~20% цены инстанса, **проверить**), либо `rclone`/`scp` на другое хранилище владельца (Backblaze B2 даёт бесплатный объём, **проверить**; Litestream как вариант с непрерывной репликацией). Раз в квартал проверять восстановление. Это единственное хранилище пользовательских данных.
- **Логи:** Docker `json-file` с ротацией (`max-size 10m`, `max-file 5`), без персональных данных и токенов в логах (логируем `user_id`, не имя).
- **Мониторинг:** внешний пинг `/health` (UptimeRobot, бесплатный план, **проверить** условия) и пинг healthchecks.io из задачи бэкапа; письмо владельцу при падении.
- **Обновления:** образы пиннить по тегу; `unattended-upgrades` для ОС; ручной `docker compose pull` для Caddy раз в месяц; Node-зависимости через Dependabot.
- **Минимальный сервер:** 1 vCPU, 1 ГБ RAM, 20–25 ГБ SSD, Ubuntu 24.04 LTS (или Debian 12), 1 ГБ swap. Потребление API ~100–150 МБ RAM. Самый дешёвый тариф Vultr достаточен (**проверить** цену и что IPv4 включён).

## 4. Безопасность

- **Секреты.** `BOT_TOKEN` и прочие значения лежат в `/opt/hayeren/.env` на сервере (владелец `deploy`, `chmod 600`), подключаются через `env_file` в compose. В репозитории только `server/.env.example` с пустыми значениями. В GitHub Secrets токен бота не нужен вообще (деплой его не касается). Токен никогда не пересылается в чат: владелец вставляет его в файл на сервере сам. При утечке: `/revoke` в BotFather, обновить файл, перезапустить.
- **Rate limiting.** Глобально 120 запросов/мин на IP, 60 запросов/мин на аккаунт; `/auth/start` 10/мин и `/auth/poll` 40/мин на IP (требования 70, 79). Ввода кода нет. Caddy за прокси: настроить `trustProxy`, чтобы видеть реальный IP. Ограничение размера тела.
- **CORS** только `https://irikkarp.github.io` (см. выше).
- **Заголовки:** HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` на API (API не отдаёт HTML, так что CSP `default-src 'none'`).
- **Фаервол:** `ufw` разрешает 22, 80, 443 (80 нужен Caddy для выпуска сертификата), остальное закрыто; дублируется Vultr Firewall. Порт API наружу не публикуется, только внутри сети compose. `fail2ban` для SSH.
- **ОС и SSH:** вход только по ключу, `PasswordAuthentication no`, `PermitRootLogin no`, отдельный пользователь `deploy`, автоматические обновления безопасности. Возможна смена порта SSH, но это не защита.
- **Приватность:** храним `telegram_id`, имя (необязательно) и учебные данные; нет аналитики. Нужны экран/текст о том, что хранится, и удаление аккаунта.
- **Проверки ввода:** схемы валидации на каждый эндпоинт; `data` записей ограничивать по размеру и допустимым полям, не доверять `store` из запроса (белый список).

## 5. CI/CD для бэкенда

- **Где код:** `server/` в репозитории `hayeren-app` (публичный). Никаких секретов, IP сервера и токенов в коде и логах CI. Адрес API публичный и попадёт в бандл фронтенда, это нормально.
- **CI:** отдельный workflow `server-ci.yml` с фильтром путей `server/**` и `shared/**`: `npm ci`, lint, форматирование, тесты (vitest, SQLite в памяти), сборка Docker-образа. Существующие workflow для `app/` не затрагиваются; deploy-pages по-прежнему срабатывает только на сборку фронтенда.
- **Деплой (рекомендация):** workflow `server-deploy.yml` по ручному запуску или по тегу `server-v*`, окружение `production` с ручным подтверждением владельца.
  1. Сборка образа и публикация в `ghcr.io/<логин>/hayeren-api:<sha>` (образ без секретов; при публичном репозитории пакет можно сделать публичным, тогда серверу не нужен токен для pull).
  2. SSH на сервер под пользователем `deploy` (ключ в GitHub Secrets `DEPLOY_SSH_KEY`, хост в `DEPLOY_HOST`, известный fingerprint в `DEPLOY_KNOWN_HOSTS`), выполняется скрипт `deploy.sh <sha>`: бэкап БД, `docker compose pull`, `up -d`, проверка `/health`, при неудаче автоматический возврат на предыдущий тег.
  3. Ключ деплоя ограничить: отдельный ключ только для этой задачи (`command="/opt/hayeren/deploy.sh"` в `authorized_keys`), без sudo, пользователь в группе docker (что фактически эквивалентно root, поэтому ключ хранится только в окружении `production`).
  Ограничение: GitHub-раннеры приходят с широкого диапазона IP, поэтому SSH придётся держать открытым для интернета (ключи + fail2ban). Альтернатива без этой дыры: **ручной деплой** с Mac владельца (`./server/deploy.sh`), для начала этого достаточно. Можно стартовать вручную, а автоматизацию добавить позже.
- **Откат:** `IMAGE_TAG=<предыдущий sha> docker compose up -d`. Миграции только вперёд и совместимые с предыдущей версией (сначала добавляем столбцы, удаляем в следующем релизе); перед каждым деплоем снимок БД, из которого можно восстановиться. Хранить последние 5 тегов образов.
- **Версионирование и changelog:** `server/CHANGELOG.md`, теги `server-vX.Y.Z`; совместимость с клиентом через `/v1` и проверку `schemaVersion`.
- **Фронтенд:** для включения аккаунтов нужна переменная `VITE_API_URL` в GitHub Variables и обновление `deploy-pages.yml` (отдельная правка, когда начнём реализацию).

## 6. Что нужно от владельца

Шаги с отметкой **[внешний/необратимый]** публикуют что-то наружу или создают внешний ресурс.

**Информация о сервере (текстом в чат, без паролей):**
- ОС и версия, тариф (CPU, RAM, диск), регион;
- публичный IPv4 (и есть ли IPv6), статичный ли;
- что уже работает на сервере (порты 80/443 заняты ли, другие сайты, Docker, nginx/apache);
- есть ли root-доступ / sudo, есть ли свободное место под бэкапы;
- включены ли Vultr Backups, нужна ли внешняя копия.

**Доступ по SSH (делает владелец сам, агенты паролей и приватных ключей не получают):**
1. На Mac: `ssh-keygen -t ed25519 -C "hayeren-deploy" -f ~/.ssh/hayeren_vultr` (парольная фраза желательна).
2. Публичный ключ (`~/.ssh/hayeren_vultr.pub`) добавить на сервер самому, например `ssh-copy-id` или через панель Vultr (SSH Keys). Приватный ключ никому не передаётся и не коммитится.
3. Агентам нужен только публичный ключ и подтверждение, что можно работать на сервере; решить, будет ли DevOps-агент получать доступ к серверу в сессии, или все команды владелец запускает сам по подготовленным скриптам (безопаснее для начала).
4. **[внешний]** Для автодеплоя позже: отдельная пара ключей, приватная часть в GitHub Secrets.

**Бот в @BotFather (делает владелец сам) [внешний]:**
1. `/newbot`, выбрать имя и username (имя публичное и менять его неудобно, например `hayeren_app_bot`).
2. Токен вида `123456:ABC...` показывается один раз в чате с BotFather. Хранить только в файле `.env` на сервере и в менеджере паролей. Не присылать в чат, не коммитить. Если токен засветился: `/revoke`.
3. Желательно задать описание, аватар, `/setcommands` (по необходимости). `/setdomain` в основном варианте не требуется.
4. Сообщить агентам только username бота (он публичный).

**Решения:**
- Согласовать вариант HTTPS: sslip.io на старт (рекомендация) или сразу купить домен (**[внешний, платный]**, ~2–12 USD/год).
- Согласовать вход через бота как основной способ.
- Где хранить внешнюю копию бэкапов (аккаунт Backblaze/другой, или платные Vultr Backups).
- Нужен ли внешний мониторинг (аккаунт UptimeRobot/healthchecks.io, **[внешний]**).
- Автоматический деплой через GitHub Actions или ручной на старте.
- Политика приватности и удаление аккаунта: нужен ли текст, кто его пишет.
- Если сервер уже занят другими сервисами: разрешить ли поставить Docker/Caddy или нужен другой способ сосуществования.
- Что делать с локальными данными при входе под чужим аккаунтом на том же устройстве (вопрос аналитику; по решению «один аккаунт на устройство» нужен явный сценарий выхода).

## 7. Оценка трудоёмкости

Оценки в рабочих днях одного исполнителя без ожиданий внешних ответов.

| Этап | Содержание | Оценка |
|---|---|---|
| 0. Подготовка сервера | пользователь, SSH-ключи, ufw, fail2ban, unattended-upgrades, Docker, swap (после получения доступа) | 0,5 дня |
| 1. Каркас бэкенда | `server/`, Fastify, Docker-образ, compose + Caddy, sslip.io и сертификат, `/health`, CORS, rate limit, миграции | 1,5–2 дня |
| 2. Вход через Telegram | таблицы, `/auth/*` (без запасного кода), бот на long polling, PKCE-подобная защита, сессии с лимитом 10 токенов, logout, удаление аккаунта, тесты | 2–2,5 дня |
| 3. API синхронизации | `/sync/push`, `/sync/pull`, общий пакет слияния `shared/` (правила 30-34, 37), слияние в транзакции, новый `seq` при отличающемся результате, курсор, бессрочные надгробия, лимиты, общий набор примеров и property-тест слияния в `server/` и клиенте | 3–4 дня |
| 4. Клиент (программист) | слой синхронизации поверх Repository, экран входа, очередь изменений, первый вход и перенос локальных данных, статусы ошибок, e2e | 4–6 дней (вне зоны DevOps) |
| 5. Бэкапы и мониторинг | скрипт бэкапа, внешняя копия, проверка восстановления, пинги | 1 день |
| 6. CI/CD | `server-ci.yml`, `server-deploy.yml` или `deploy.sh`, откат, документация в `docs/devops/` | 1–1,5 дня |
| 7. Переход на домен (если решим) | DNS, Caddyfile, `VITE_API_URL`, `/setdomain` при необходимости | 0,5 дня |

Итого серверная часть и DevOps примерно 9,5–12,5 дней (вынос слияния в `shared/` с общими тестами добавил около дня), вместе с клиентом 14–19 дней. Последовательность: 0 -> 1 -> (2, 3) -> 4 -> 5 -> 6, этап 6 можно начать после 1.

## Риски

- **Сторонний DNS (sslip.io/DuckDNS):** сбой сервиса или лимит Let's Encrypt остановит выдачу и продление сертификата. Митигация: ZeroSSL как запасной ЦС в Caddy, конфигурируемый адрес API, план перехода на купленный домен.
- **Адрес API в опубликованных мобильных сборках** нельзя поменять без релиза. Митигация: домен до сборки Capacitor.
- **Единая точка отказа и потеря данных:** один сервер, один файл БД. Митигация: бэкапы вне сервера и регулярная проверка восстановления; приложение офлайн-первое, поэтому при простое сервера локальные данные работают.
- **Утечка токена бота:** захват бота. Митигация: файл с правами 600, не логировать, `/revoke`; сам по себе токен не раскрывает данных пользователей, они лежат в нашей БД.
- **Telegram:** зависимость от доступности Telegram у пользователей и у сервера; вход необязателен, так что приложение продолжает работать без него. Пользователям без Telegram аккаунт недоступен (альтернативных способов нет по решению владельца).
- **Конфликты синхронизации:** расхождение часов клиентов и разное поведение слияния на клиенте и сервере. Митигация: одна общая функция слияния в `shared/`, общие тесты и property-тест, обрезка будущих меток, серверный `seq`.
- **Поверхность атаки SSH для автодеплоя:** раннеры GitHub с широких IP. Митигация: ключ + fail2ban, или ручной деплой.
- **Публичный репозиторий:** случайный коммит секрета. Митигация: `.env` в `.gitignore`, GitHub secret scanning и push protection (включить, **проверить** доступность для публичных репозиториев).
- **iOS PWA:** нет фоновой синхронизации, возможны очистки хранилища. Митигация: синк при запуске и возврате в приложение.
- **Непроверенные факты** помечены «проверить» и должны быть подтверждены до начала реализации (особенно: лимиты LE для sslip.io, поведение BotFather с `github.io`, формат payload deep link).
